# Architecture

## The layers

Everything the application is made of lives under `src/`, in six folders. They are
ordered: a layer may depend on the ones above it in this list, never on the ones below.

| Layer                | Holds                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| `src/core`           | What every other layer may use and that belongs to no problem in particular — a clock, a result type.         |
| `src/domain`         | The problem itself: notes, clefs, what a correct answer is. Ports the domain needs are declared here.         |
| `src/usecases`       | What the application does, one file per thing it does. A use case declares the port it needs and receives it. |
| `src/infrastructure` | The adapters: Expo and React Native SDKs, the file system, the DI container.                                  |
| `src/components`     | React components that render no route — the container provider, later the design system.                      |
| `src/app`            | The Expo Router routes. A file here is a screen or a layout.                                                  |

The direction is **inwards only**: a use case never imports an adapter, the domain never
imports a use case, `src/core` imports nothing of the others. A use case that needs the
outside world declares the shape it needs — `SpeechRecognizer`, `AppVersionReader` — and
`src/infrastructure` provides an implementation.

**Checked** by `bun run arch` (dependency-cruiser, rules in `.dependency-cruiser.json`),
which is a step of `tools/verify`. Each rule carries its reason in the config; read it
there rather than here, so the two cannot disagree.

Beyond the direction, the same check refuses:

- a cycle between two modules;
- a React, React Native or Expo Router import below `src/app` and `src/components` — the
  inner layers must stay runnable in plain Bun, with no renderer;
- an Expo import in `src/core`, `src/domain` or `src/usecases` — wrapping a platform SDK
  is infrastructure's job;
- a `devDependency` reached from application code, which would be missing from a
  production install;
- an orphan module, which is either dead or wired by a path the graph cannot see.

## Wiring

Dependencies are resolved by an Inversify container built in `src/infrastructure`. The
identifiers live in `src/infrastructure/symbols.ts`, typed by the port they stand for, and
a component reaches one through `useService` from `src/components/container-provider.tsx`.

A screen therefore knows a symbol and a port, never an adapter. Swapping the adapter is a
single line in the container.

## Native projects

`ios/` and `android/` are generated by the Expo prebuild from `app.json` and are not
committed. Nothing is edited there: a change made by hand is lost at the next prebuild.
Configuration goes to `app.json` or to a config plugin.

## The speech bench

`bench/` is not part of the application and is never imported by it. It replays a corpus
of recordings through a speech recogniser and publishes the figures CLE-17 decides on.
It reuses the domain and the use cases — the bench is one more caller of
`src/usecases/replay-speech-corpus.ts`, which is the point: the inner layers run outside
the app.

`bench/corpus/README.md` holds the recording protocol. `tools/bench-reproducible`, a step
of `tools/verify`, replays a fixture corpus twice and refuses any difference between the
two reports.
